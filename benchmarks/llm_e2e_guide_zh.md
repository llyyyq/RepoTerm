# RepoTerm 真实 LLM 端到端评测使用说明

## 1. 这套评测解决什么问题

项目原有的 `tests/test_agentops_scenarios.py` 使用脚本化 `ModelAdapter`：测试代码预先规定模型下一步要调用哪个工具，再验证 Agent Runtime 是否正确执行。这种测试稳定、便宜，适合回归状态机、权限、工具和恢复链路，但不能证明真实 LLM 会自己做出正确决策。

本评测增加第二层证据：模型输出来自你本地配置的真实 Provider。模型必须自己完成检索、选择工具、修改代码、阅读失败反馈、重新测试和给出最终回答。评测器不凭“回答看起来不错”判分，而是检查文件哈希、独立 Pytest、禁止路径、权限记录和会话恢复状态。

因此两层测试应当分开表述：

- 20 个确定性离线场景：证明 Runtime 和工具链路在预定输入下符合设计。
- 5 个真实模型任务：证明真实 LLM 能否通过这套 Runtime 完成端到端仓库任务。

## 2. 五个任务及其存在理由

| 任务 | 初始状态 | 模型必须完成的行为 | 主要判分证据 |
| --- | --- | --- | --- |
| 仓库检索与依据回答 | 测试原本通过 | 用检索和读取工具找到真实实现，不改文件 | 路径、符号、业务规则、grep/read Trace、零文件变化 |
| 代码修改与测试验证 | 测试原本失败 | 修复字符串规范化并运行测试 | 源文件变化、tests哈希不变、Agent测试证据、独立Pytest通过 |
| 测试失败后的修复恢复 | 测试原本失败 | 先运行失败测试，再依据报错修复并重试 | Trace中“先失败后成功”、独立Pytest通过 |
| 权限拒绝后的替代方案 | 测试原本失败 | 首次按要求修改受保护文件；被拒绝后遵循反馈改另一文件 | 拒绝记录、受保护文件不变、替代文件变化、测试通过 |
| 写入中断与会话恢复 | 测试原本失败 | 成功写入后被注入中断；从持久化Session继续验证 | Session重新加载、恢复阶段测试、恰好1个Checkpoint、独立Pytest通过 |

检索任务的基线测试应当通过；其余四个任务的基线测试必须失败。这样可以排除“模型什么都没修，仓库原本就通过”的假成功。

## 3. 一次任务的完整执行链路

1. 评测器在 `.temp/llm_e2e/runs/` 下创建唯一的隔离仓库。
2. 记录业务文件的基线 SHA-256 哈希，后续用来判断哪些文件真的变化。
3. 只注册仓库任务需要的内置工具：目录、检索、读取、写入、编辑、补丁和测试工具。评测不开放通用 Shell，避免模型绕过文件审批修改判分基准。
4. 创建最小权限策略：正常 `src/` 修改允许一次，`tests/` 永远拒绝，权限任务的 `src/settings.py` 返回带中文反馈的拒绝。
5. 由真实模型和 `run_agent_turn` 多轮交互。模型输出不是评测器预先写好的。
6. Trace记录阶段、停止原因、工具参数/结果、权限决策和恢复动作；只记录 thinking 字符数，不保存隐藏思维内容。
7. Agent停止后，评测器在模型之外再次执行独立 Pytest，避免模型伪造测试结果。
8. Grader把 Trace、文件哈希、独立测试和Session状态组合成确定性通过/失败结果。
9. 单次证据写入 `trace.json`，整批结果写入 JSON，并生成中文 Markdown 报告。

## 4. 为什么权限审批是脚本化的

正式批量评测需要同一输入重复三次。如果每次由人临时决定是否批准，结果会混入人的差异，无法公平比较。因此评测中的审批策略是固定的，但模型仍然会收到真实的工具失败和用户反馈，必须自己决定下一步。

这项测试证明“Agent在权限拒绝后能否恢复”，不证明“TUI里的真人点击体验”。后者应当另做一次手工冒烟测试并保留截图或录屏。

## 5. 如何运行

以下命令都在项目根目录、已激活的 `agent-env` 终端中执行。

### 第一步：零费用预检

```powershell
python benchmarks/llm_e2e_eval.py --dry-run --all
```

它只创建五个夹具并检查基线测试，不读取模型配置、不调用 API。中文报告位于 `benchmarks/llm_e2e_dry_run.md`。

### 第二步：单任务调试

建议先从修改任务开始，确认模型、工具和报告链路均可工作：

```powershell
python benchmarks/llm_e2e_eval.py --task code_modification --runs 1 --confirm-live
```

`--confirm-live` 是付费调用保护开关；没有它，程序会在加载 Provider 前停止。

### 第三步：五任务各运行一次

```powershell
python benchmarks/llm_e2e_eval.py --all --runs 1 --confirm-live
```

先阅读报告和失败 Trace。如果某个任务是因为 Prompt 或 Grader设计错误而失败，应先修正评测器，再开始正式统计，不能一边正式运行一边偷偷改变判分口径。

### 第四步：正式运行五任务各三次

```powershell
python benchmarks/llm_e2e_eval.py --all --runs 3 --confirm-live
```

这会得到 15 次真实模型任务运行。注意“一次任务运行”通常包含多轮模型 API 调用，不能把 15 次任务等同于 15 次 API 请求。

## 6. 输出文件

- `benchmarks/llm_e2e_results.md`：给人阅读的中文正式报告。
- `benchmarks/llm_e2e_results.json`：后续画图、统计和自动检查使用的机器数据。
- `.temp/llm_e2e/runs/<run-id>/trace.json`：单次运行的完整可观察证据。
- `.temp/llm_e2e/runs/<run-id>/workspace/`：该次任务结束时的仓库状态。
- `.temp/llm_e2e/runs/<run-id>/runtime/`：隔离的Session、权限和审计状态。

Trace会脱敏常见密钥字段并替换绝对路径，但将报告公开到 GitHub 前仍应人工搜索 `api_key`、`auth_token`、`Authorization` 等字段。

## 7. 报告指标怎么理解

- 任务运行成功率：所有确定性 Grader 全部通过的运行数 ÷ 总运行数。
- 异常恢复成功率：测试失败、权限拒绝、会话恢复三个任务中的通过数 ÷ 这些任务的运行数。
- 有证据完成率：修改类任务中，同时具备 Agent 内部成功测试记录和评测器独立 Pytest 通过的比例。
- 工具参数有效率：没有出现 Schema 参数错误或未知工具错误的调用数 ÷ 全部工具调用数。
- P50/P95耗时：任务端到端耗时的中位数和95分位数。
- 失败归因：按 Provider错误、工具参数、工具执行、权限恢复、验证失败、最大步数等类别归档。

Token是按消息字符估算，适合相同配置下做横向比较；成本依赖 Provider是否返回用量以及项目价格表，报告中的0不能自动解释为免费。

## 8. 简历数字如何写

只有正式运行完成后，才能把报告中的真实数字代入简历。推荐句式：

> 构建20个脚本化场景的确定性Runtime回归集，并补充5类真实LLM仓库任务，各重复3次；以文件哈希、独立Pytest、禁止路径和恢复状态进行判分，任务成功率为`[报告数字]`，异常恢复成功率为`[报告数字]`，并通过Trace完成失败归因。

不要写“60次真实LLM全部通过”。60次是20个脚本化离线场景重复三轮；真实模型的正式口径是5个任务各三次，共15次任务运行，两者验证的问题不同。
